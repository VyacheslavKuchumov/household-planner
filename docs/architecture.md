# Архитектура Household Planner

## Реализованный модуль аккаунтов

Приложение состоит из Vue SPA и Scala backend на ZIO HTTP. Сервер хранит учётные записи и сессии в PostgreSQL. Локальные списки пользователей, переключение демо-ролей и имитация отправки писем удалены из frontend.

Реализованы регистрация, JWT-вход, обновление/отзыв сессий, редактирование никнейма и своего пароля, подтверждение/отклонение регистраций, блокировка/восстановление доступа, отправка reset-ссылок через SMTP и журнал действий. Пользователи также могут создавать и просматривать свои домохозяйства.

Планировщик дел, запасы, бюджет, расписания и отдых пока представлены моделью PostgreSQL и дальнейшим планом. Они не должны считаться готовыми прикладными модулями только потому, что таблицы уже существуют.

## Стек и структура

- `web/` — Vue 3, TypeScript, Composition API (`<script setup>`), Vuetify, Vue Router. Hash routing позволяет размещать SPA на статическом хостинге и хранить reset-токен во fragment URL.
- `backend/` — Scala 3, ZIO 2, ZIO HTTP; модульный монолит.
- `auth/Models.scala` — DTO, валидация, правила доступа.
- `auth/AuthService.scala` — прикладные сценарии; все JDBC, SMTP и парольные вычисления вынесены в blocking effects.
- `auth/AuthRepository.scala` — параметризованные SQL-запросы и транзакции модуля аккаунтов; JDBC через HikariCP. Явные блокировки строк обеспечивают ротацию токенов, сериализацию bootstrap и безопасную смену пароля.
- `auth/Security.scala` — Argon2id через Password4j, подписанные RSA JWT через Nimbus JOSE + JWT, случайные непрозрачные токены, rate limiter.
- `auth/Api.scala` — маршруты, аутентификация, Origin/CORS, CSRF, безопасные JSON-ошибки и request id.
- `auth/Mailer.scala` — SMTP с таймаутами и обязательным STARTTLS в production-конфигурации.
- `backend/src/main/resources/db/migration/` — Flyway SQL-миграции; применяется один и тот же набор для local/test/production.

Quill остаётся вариантом для будущих репозиториев доменных модулей. Текущий auth-репозиторий использует подготовленные JDBC-запросы: транзакции и `FOR UPDATE` записаны явно и работают с общим пулом DataSource.

## Аккаунты, личный кабинет и администратор

| Состояние | Разрешённые действия |
| --- | --- |
| Без сессии | Регистрация, вход, завершение сброса пароля по действующему токену |
| `PENDING` | Личный кабинет, изменение своего никнейма и пароля, выход |
| `ACTIVE` | Личный кабинет и домохозяйства, в которых есть membership |
| `ACTIVE` + `PLATFORM_ADMIN` | Управление аккаунтами и журнал аудита |
| `password_change_required` | Просмотр своего профиля, обязательная смена пароля, выход; остальные действия закрыты |
| `SUSPENDED` / `REJECTED` | Вход и защищённые операции закрыты |

Роль платформы хранится в `user_role`, независимо от `membership.role`. Владелец домохозяйства не получает права администратора. Самостоятельное изменение своего статуса запрещено; последнего активного администратора нельзя отключить.

Регистрация создаёт `PENDING`. Администратор переводит его в `ACTIVE`, записывая `approved_at` и `approved_by_user_id`. Это административное подтверждение аккаунта. Поле `email_verified_at` зарезервировано для будущего подтверждения владения email и сейчас не является дополнительным барьером входа: отдельный email-verification workflow ещё не реализован.

При первом запуске backend внутри транзакции с advisory lock создаёт `admin` / `admin`, если платформенного администратора ещё нет. У него сразу установлен `password_change_required`. Одноразовый маркер `system_bootstrap` исключает восстановление стандартного пароля при следующих запусках. Сменить первый пароль нужно в доверенном окружении до публичного открытия приложения. В БД хранится Argon2id-хеш.

Пользователь может менять только свой никнейм (`display_name`) и свой пароль. Изменение пароля требует текущий пароль, включая первичный `admin`. Минимальная длина нового пароля — 12 символов; максимум — 256. После смены завершаются все сессии, затем пользователь входит снова.

## JWT и сессии

Access JWT действует 10 минут, подписывается RSA/RS256 и содержит `iss`, `aud`, `sub`, `sid`, `jti`, `iat`, `exp`; тип — `at+jwt`. Проверка фиксирует алгоритм и `kid`, проверяет подпись, issuer, audience и время. Установленная пара ключей должна совпадать; RSA — не менее 2048 бит. Development helper генерирует 3072 бита.

Клиент хранит access-токен только в памяти. Refresh-токен — случайные 256 бит; он передаётся в host-only `HttpOnly` cookie с `Secure` в production. В PostgreSQL хранится только SHA-256-хеш непрозрачного токена. Абсолютный срок сессии — 30 дней; ротация не продлевает его бесконечно.

Каждый refresh помечает старую запись использованной и выпускает новую в одной транзакции. Сначала блокируется пользователь, затем сессия и токен. Повтор использованного токена отзывает всю сессию. Ошибка возвращается после commit отзыва, чтобы rollback не восстановил скомпрометированную сессию. Уникальные индексы и составной FK обеспечивают одну текущую цепочку и замену только внутри своей сессии.

На каждом защищённом запросе API сверяет `sid`, статус пользователя и актуальную роль с БД. Поэтому JWT сам по себе не открывает доступ к чужому дому или админке. Блокировка и выход сразу отзывают доступ, даже если JWT ещё не истёк. Vue guards управляют навигацией; backend проверяет те же ограничения независимо от UI.

Refresh требует разрешённый `Origin` и double-submit CSRF-токен: `/api/auth/csrf` выдаёт случайное значение в ответе и cookie, следующий refresh передаёт его в `X-CSRF-Token`. Остальные защищённые операции используют только Bearer, а не cookie как удостоверение личности. CORS разрешает только настроенные origins и credentials. Клиент объединяет одновременные refresh-запросы и использует Web Locks для ротации между вкладками.

Одна пара JWT-ключей загружается при старте. При её замене старые access JWT перестают приниматься; сохранённая refresh-сессия может получить новый access JWT. Проверка одновременно нескольких verification keys пока не реализована.

## Сброс пароля и аудит

Администратор запрашивает отправку одноразовой ссылки на email пользователя. Случайный токен действует 30 минут, в БД хранится только хеш. Новый запрос отзывает предыдущую неиспользованную ссылку. Администратор не получает токен или пароль в ответе API.

Письмо действительно отправляется через SMTP. Если доставка завершается ошибкой, выданный токен отзывается, API возвращает 503, интерфейс не сообщает об успешной отправке. URL имеет вид `/#/reset-password?token=...`: fragment не попадает в HTTP access logs. Frontend убирает токен из адресной строки после чтения и не сохраняет его в storage.

Погашение reset-токена и смена парольного хеша выполняются атомарно с блокировкой записи. Повторная попытка, истёкшая/отозванная ссылка или заблокированный аккаунт отвергаются. Сброс завершает все сессии, но не одобряет ожидающую регистрацию.

`admin_audit_log` фиксирует подтверждение/отклонение, блокировку/восстановление, запрос и завершение reset, собственную и первичную смену пароля. Аудит не содержит пароль, JWT, reset-токен или ссылку. В журнале доступны последние 100 событий; удаление записей через API не предусмотрено. Rate limits применяются к входу, регистрации, парольным операциям и отправке reset.

Профиль JWT и ротация сверены с [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725) и [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700); сброс — с [OWASP Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html). ZIO HTTP request/cookie APIs описаны в [официальной документации](https://ziohttp.com/reference/headers/session/cookies/).

## Соединение с PostgreSQL и Docker

HikariCP предоставляет ограниченный пул JDBC-соединений. Каждая операция возвращает соединение после завершения; транзакции располагаются на границе сценария. Параметры: `DB_URL`, `DB_USER`, `DB_PASSWORD`/`DB_PASSWORD_FILE`, `DB_POOL_SIZE`.

`compose.yaml` запускает Traefik, Nginx/Vue, Scala API, PostgreSQL и одноразовый Flyway. Порядок: здоровая БД → успешные миграции → API. PostgreSQL не публикует порт наружу. Traefik маршрутизирует `/api` в API, остальные пути — в SPA и завершает HTTPS. Приватный ключ передаётся через secret file и копируется в tmpfs перед переходом JVM на непривилегированного пользователя.

`GET /api/health` проверяет процесс; `GET /api/ready` выполняет запрос к необходимой схеме PostgreSQL. При отсутствии конфигурации, ключей или миграций backend не запускается с фиктивным хранилищем.

`compose.dev.yaml` содержит локальную БД и Mailpit. Helper-скрипты запускают БД, применяют миграции и загружают идемпотентные base/demo SQL. `compose.test.yaml` использует одноразовые контейнеры и собственные порты, без dev/prod volumes. Подробности — [deployment.md](deployment.md).

## Автоматические проверки

- `AuthSecuritySpec` — проверка подписи/срока/issuer/audience/типа JWT, подмены алгоритма, salted Argon2id, матрицы прав и rate limits.
- `AuthIntegrationSpec` — настоящая PostgreSQL в отдельной случайной схеме, Flyway-миграции, bootstrap, nickname/password, обновление прав после approve, membership isolation, refresh replay и конкурентная ротация, одноразовые/истёкшие reset-токены, SMTP failure, отзыв и аудит. Дополнительно вызываются HTTP routes для проверки 401/403 и CSRF.
- Vitest + Vue Test Utils — поведение формы входа и API-клиента, повтор запросов, объединение refresh, неуспешный login и сетевые ошибки.
- Playwright — реальный API и SMTP/Mailpit: первичный admin, регистрация, ограниченный кабинет, одобрение, домохозяйство после reload, смена/восстановление пароля, блокировка сессий и аудит. Авторизация не подменяется.
- CI собирает frontend и запускает все наборы с PostgreSQL/Mailpit. При падении сохраняются trace, screenshot и server log для тестового окружения.

Команды и условия запуска — в README. Наличие CI-конфигурации не означает прошедший прогон: результат нужно проверять по реальному запуску. Конфигурации Compose проверяются отдельно от браузерных/DB проверок.

## Следующие доменные модули

1. Повторяющиеся задачи: шаблон отдельно от экземпляра и истории выполнения, ручное назначение/перенос/подмена.
2. Графики 5/2 и 2/2: выбранные рабочие дни или цикл от anchor date; смены могут пересекать полночь.
3. Нейтральные интервалы недоступности: только участник и даты, без причины, состояния здоровья и личных пояснений.
4. Личный/общий защищённый отдых; автоматическое распределение исключает смены, недоступность и отдых.
5. Запасы меняются через журнал движений; покупка атомарно связывает движение и бюджетную транзакцию.
6. Бюджет хранит суммы целым числом в минимальных единицах валюты.
7. Планировщик — детерминированный Scala-доменный компонент, объясняющий ограничения и рекомендации; публикация распределения требует подтверждения пользователя.

Все будущие доменные запросы ограничиваются проверенным `membership` и `household_id`. Резервное копирование, ограниченная DB-роль runtime и эксплуатационные лимиты должны быть настроены для реального окружения.
